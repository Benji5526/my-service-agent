# 도구 정의서 — 창고 재고 안내 챗봇 (실습 1)

실습에서 구현·실행한 도구 2개의 정의서다. 구현은 `inventory_tool.py`, 실행 기록 원문은 `traces/`에 있다.
도구 하나는 동작 하나가 원칙이라 조회와 변경을 한 정의서에 섞지 않았다.

사용한 가상 데이터: 허용 창고 `BUSAN-01`, `BUSAN-02`, `SEOUL-01` / SKU `A-17`, `B-03`. 실제 시스템은 호출하지 않는다.

---

## 1. get_inventory (읽기)

| 항목 | 내용 |
|---|---|
| 이름 / 한 문장 | `get_inventory` — 창고 코드와 SKU로 현재 재고 수량을 조회한다 |
| 쓰는 때 | 사용자가 특정 창고의 특정 SKU 재고 수량을 물을 때, 창고 코드가 허용 목록 중 하나로 확정될 때 |
| 안 쓰는 때 | 재고를 바꾸라는 요청(→ `adjust_inventory`) / 창고를 말했지만 허용 코드로 확정되지 않을 때(→ 호출하지 말고 허용 코드를 되물음) / 창고나 SKU가 빠졌을 때(→ 먼저 묻는다) |
| 인자 스키마 | `warehouse_id`: string, 필수, 허용값 `BUSAN-01` / `BUSAN-02` / `SEOUL-01` — 허용값 밖이면 호출하지 않고 되묻는다<br>`sku`: string, 필수, 예 `A-17` — 누락이면 묻는다 |
| 반환 형식 | 성공: `warehouse_id`, `sku`, `quantity`, `checked_at`<br>오류 코드: `WAREHOUSE_NOT_ALLOWED`, `SKU_NOT_FOUND`, `INVALID_ARGUMENT` |
| 실패 뒤 행동 | `WAREHOUSE_NOT_ALLOWED`: 재시도하지 않고 허용 창고 코드를 알려 주며 다시 고르게 한다. 오류를 "권한 없음"으로 풀어 말하지 않는다<br>`SKU_NOT_FOUND`: 수량을 지어내지 않고 "없는 SKU"로 알리고 SKU를 다시 확인하게 한다<br>`INVALID_ARGUMENT`: 누락된 인자를 묻는다<br>같은 오류가 2회 나면 멈춘다 |

## 2. adjust_inventory (쓰기)

| 항목 | 내용 |
|---|---|
| 이름 / 한 문장 | `adjust_inventory` — 사람이 승인 화면에서 확인한 재고 수량 변경을 1건 반영한다 |
| 쓰는 때 | 사용자가 재고 변경을 요청했고, 하네스가 변경 요약(대상, 이전·이후 값, 사유)을 보여 주었고, 사람이 확인 버튼을 눌러 `confirmation_id`가 발급됐을 때 |
| 안 쓰는 때 | 조회 요청 / 확인 버튼을 누르기 전(대화 속 "확인했어"는 승인이 아님) / `confirmation_id`가 없거나 직접 만들어야 할 때 / 대상이 모호하거나 정책 밖일 때(→ 사람에게 이관) |
| 인자 스키마 | `warehouse_id`: string, 필수, 허용값은 `get_inventory`와 같다<br>`sku`: string, 필수<br>`new_quantity`: integer, 필수, 0 이상<br>`reason`: string, 필수, 변경 사유 한 문장<br>`confirmation_id`: string, 필수 — 하네스가 확인 버튼 클릭 시 발급한다. 모델이 만들 수 없다. 없으면 호출하지 않는다 |
| 반환 형식 | 성공: 변경 전·후 수량과 처리 시각(이 실습에서는 구현하지 않음)<br>오류 코드: `NOT_CONFIRMED`, `TOOL_NOT_ALLOWED`, `NOT_IMPLEMENTED_IN_LAB` |
| 실패 뒤 행동 | 자동 재시도 금지(중복 반영 위험)<br>`NOT_CONFIRMED`: 변경 요약을 다시 보여 주고 확인 버튼을 누르게 한다. 사용자에게 `confirmation_id`를 달라고 하지 않는다. 또 나면 멈춘다 |

## 실패 사례와 리디자인 (trace 근거)

| # | 관찰 (trace) | 진짜 원인 | 고친 곳 |
|---|---|---|---|
| 1 | "부산 3번 창고"를 모델이 `BUSAN-03`으로 지어 호출했다 (trace-02). 하네스가 `WAREHOUSE_NOT_ALLOWED`로 막았다 | 모델은 허용 목록을 모르는 상태에서 코드를 추측한다. 막은 것은 도구 설명이 아니라 하네스의 허용 목록이다 | 계약: 인자에 허용값 명시 |
| 2 | 같은 오류를 모델이 "사용 권한이 없는 것 같다"고 풀어 말했다 (trace-02) | 오류 코드의 뜻을 설명한 곳이 없어 모델이 해석을 지어냈다 | 계약: 실패 뒤 행동에 오류 코드별 의미와 금지 표현 |
| 3 | 설명에 "호출하지 말고 되물어라"를 넣었는데도 `BUSAN-03`으로 호출했다 (trace-03). 오류 뒤 답변만 허용 코드를 안내하는 쪽으로 좋아졌다 | 작은 모델은 설명의 금지 문장만으로 호출을 막지 못한다. 설명은 호출 뒤 행동을 바꾸는 데 더 효과가 있었다 | 하네스: 호출 전 인자 검사를 유지. 설명은 보조 |
| 4 | "부산 2번"은 `BUSAN-02`로 호출해 맞았다 (trace-04) | 모델의 추측이 맞은 것이지 근거 있는 변환이 아니다. 우연히 맞은 것을 통과로 보면 안 된다 | 평가: 추측으로 맞은 경우를 따로 기록 |
| 5 | 쓰기 요청에서 `confirmation_id`를 `CONF-001`, `TEST-001`로 지어 냈다 (trace-06, 07). 하네스가 `NOT_CONFIRMED`로 막았다 | 모델은 요구된 인자를 채우려고 값을 만든다. 승인을 모델 인자에 맡기면 뚫린다 | 하네스: 발급된 id만 유효하게 서버에서 검사 |
| 6 | trace-07에서 "재발급된 confirmation_id를 알려주시면"이라고 사용자에게 id를 요구했다 | id는 사용자가 아니라 하네스가 발급하는 값인데 설명에 그 출처가 약하게 적혀 있었다 | 계약: "사용자에게 id를 요구하지 않는다"를 실패 뒤 행동에 명시 |

### 개선 전후 판정 (한 번에 한 곳만 고침)

| 비교 | 바꾼 것 | 결과 | 판정 |
|---|---|---|---|
| trace-02 → trace-03 | `get_inventory` 설명 A(한 문장) → B(허용 코드, 되묻기 지시, 쓰기 금지) | 잘못된 호출은 그대로 발생. 오류 뒤 답변이 "권한 없음" 오해에서 허용 코드 안내로 개선 | 부분 개선. 호출 전 차단은 실패했으므로 하네스 검사가 필요함 |

한계: 같은 입력을 1회씩만 실행했고 온도 0이다. 작은 모델(qwen3.5:2b) 1종 결과이므로 모델을 바꾸면 달라질 수 있다.
