# 룰북 `inventory_tool.py` 실습 기록 (실습 2: 도구 실행 · trace · 경계 사례)

룰북 5번 실습 2의 코드(`inventory_tool.py`)를 **수정하지 않고** 룰북 명령 그대로 실행하고, 경계 사례 실험을 더해 trace를 남겼다.
앞서 직접 만든 `my-agent/inventory_tool.py`(별도 구현)와는 다른 도구다. 이 문서는 룰북 코드의 결과만 다룬다.

## 구성

| 파일 | 내용 |
|---|---|
| `inventory_tool.py` | 룰북 코드 원본 (수정 없음) |
| `run_trace.py` | 실행하고 룰북 trace 형식으로 `traces/trace-NN.txt`를 남기는 도우미. 요청 문장·도구 설명을 바꾼 실행은 원본을 건드리지 않고 `variants/`에 복사본을 만들어 실행한다 |
| `variants/inventory_tool_NN.py` | 요청 문장이나 설명을 바꾼 실행용 복사본 |
| `traces/trace-01.txt` ~ `trace-07.txt` | 실행 기록 원문 (덮어쓰지 않고 번호를 올림) |

실행 명령은 룰북 그대로다: `uv run --with langchain --with langchain-ollama python inventory_tool.py`.
룰북 예시 trace와 같이 `실행 조건`, `요청`, `[1] 모델의 요청`, `[2] 하네스의 실행 결과`, `[3] 결과를 읽은 최종 답` 순서이며, 룰북에 없는 `변경점`, `실험 의도` 항목을 추가했다.

## 룰북 도구의 동작 (코드에서 확인한 것)

- 허용 창고는 `SEOUL-01`, `BUSAN-02` 두 개뿐이다. 그 밖의 코드는 `{"error": "WAREHOUSE_NOT_ALLOWED"}`.
- 허용 창고면 **어떤 SKU든** 수량 7을 돌려준다. 고정값이다.
- 도구 설명은 "INVALID_SKU이면 SKU를 확인해 달라고 물어야 합니다"라고 하지만, 코드는 `INVALID_SKU`를 반환하지 않는다. 설명과 구현이 맞지 않는다.
- 최종 답은 코드가 `r2.content[:120]`으로 잘라 출력한다. 긴 답은 끝이 잘려 보인다.

## 결과

| trace | 요청 | 모델의 호출 | 하네스 결과 | 관찰 |
|---|---|---|---|---|
| 01 | BUSAN-02 창고의 SKU A-17 | `BUSAN-02`, `A-17` | 수량 7 | 룰북 예시와 같은 동작 (최종 답의 표기만 다름) |
| 02 | **부산 3번** 창고의 A-17 | **`BUSAN-02`**, `A-17` | 수량 7 | 오류 없이 **다른 창고로 바꿔** 조회하고 "BUSAN-02에서 7개"라고 답함 |
| 03 | 02와 같음, 도구 설명에 "허용 코드가 아니면 호출하지 말고 되물어라" 덧붙임 | **`BUSAN-02`**, `A-17` | 수량 7 | 설명을 바꿔도 02와 같은 호출 |
| 04 | **부산 2번** 창고의 A-17 | `BUSAN-02`, `A-17` | 수량 7 | 02(부산 3번)와 **호출이 완전히 같음** |
| 05 | BUSAN-01 창고의 A-17 | `BUSAN-01`, `A-17` | `WAREHOUSE_NOT_ALLOWED` | 최종 답이 BUSAN-01을 "승인된 창고"라 하고, 요청하지 않은 `A-12`를 언급함 |
| 06 | **창고 없이** "A-17 재고" | `A-17`, **`SEOUL-01`** | 수량 7 | 사용자가 말하지 않은 창고 코드를 모델이 채움 |
| 07 | SEOUL-01 창고의 **Z-99** | `Z-99`, `SEOUL-01` | 수량 7 | 도구가 SKU를 검증하지 않아 없는 SKU도 7개로 답함 |

## 해석

1. **조용한 오답이 가장 위험하다 (02, 03, 04, 06).** 모델이 "부산 3번"을 `BUSAN-02`로, 창고 누락을 `SEOUL-01`로 바꿔 넣었고, 두 값 모두 허용 코드라 하네스가 막지 못했다. 사용자는 오류를 보지 못하고 다른 창고의 수량을 받는다. 룰북이 3단계에서 예고한 경우("부산 3번"을 `BUSAN-02`로 바꿔 버림)가 그대로 나타났다.
2. **02와 04의 호출이 같다.** 번호(2번/3번)와 상관없이 "부산"을 `BUSAN-02`로 대응한 것으로 보인다. 04가 맞은 것은 우연으로 봐야 한다.
3. **설명 한 줄 추가(03)로는 호출 전 행동이 바뀌지 않았다.** 이 모델은 작은 모델(2B)이고, 도구 설명의 금지 문장이 호출을 막지 못했다. 막을 수 있는 곳은 하네스의 검사(예: 사용자가 말한 창고 표현이 허용 코드와 정확히 일치하는지)다.
4. **오류 코드가 반환돼도 최종 답은 믿을 수 없다 (05).** 오류를 정확히 받았는데도 답에 `A-12`가 나왔고 BUSAN-01을 "승인된 창고"라고 했다. 하네스가 오류를 돌려주는 것과 모델이 그것을 정확히 전달하는 것은 별개다.
5. **도구 정의와 구현이 어긋나면 평가할 수 없다 (07).** 설명이 `INVALID_SKU`를 약속하지만 구현이 없어서, 없는 SKU에 대한 모델의 반응을 시험하지 못했다.

## 한계

- 모델 1종(`qwen3.5:2b`), 문항당 1회 실행이다. 온도 0이라 같은 입력은 거의 같은 결과가 나오지만 통계가 아니다.
- 03은 설명을 한 문장만 바꾼 한 번의 비교다. 다른 문구나 더 긴 설명은 시험하지 않았다.
- 앞서 만든 별도 구현(`my-agent/inventory_tool.py`)과 결과가 다른 부분(예: 그쪽은 "부산 3번"을 `BUSAN-03`으로 지어 호출해 하네스가 막았다)은 시스템 지시, 호출 라이브러리, 도구 설명이 모두 달라 원인을 분리하지 못했다.
- 모든 trace는 `PYTHONUTF8=1`을 설정해 실행했다(Windows 한글 환경의 출력 인코딩 문제를 피하기 위해).
